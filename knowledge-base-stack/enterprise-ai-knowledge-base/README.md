# 企业 AI 知识库建设、治理与应用手册

> 版本：v1.0 · 适用范围：企业内部知识管理、RAG、Copilot、AI Agent 与受控工作流

## 1. 目的与边界

本手册用于将分散在 Notion、Confluence、SharePoint、Git、CRM、工单、文件盘和业务系统中的企业知识，建设成**可信、可控、可检索、可执行**的 AI 知识平台。

目标不是做一个“文件聊天机器人”，而是让员工和 AI 在正确权限、最新版本和可引用证据下完成问答、决策支持与业务流程协作。

```text
权威业务源 → 接入与清洗 → 知识治理与权限 → 混合检索 → RAG / Agent → 引用答案与行动
                      ↑                                           ↓
                  运营、评测、审计、反馈、更新与下线  ←────────────┘
```

### 1.1 成功标准

- 用户能在 30 秒内找到政策、流程、产品或项目问题的可信答案，并看到来源与版本。
- 用户只能检索其已有权限的数据；原文、chunk、embedding、缓存和摘要均不能越权泄露。
- 关键知识均有明确所有者、数据分类、有效期、复审日期和权威来源。
- 任何 AI 回答、工具调用和高风险操作均可追溯、可评测、可停用。
- 知识库能够降低重复问答和信息搜寻成本，而不是制造一个无人维护的“第二文件库”。

### 1.2 非目标

- 不复制并取代 ERP、CRM、合同库、Git 或文档系统的事实来源。
- 不将全部企业资料无差别导入向量库。
- 不让 RAG 或 Agent 代替高风险审批、合规判断或最终业务决策。
- 不以模型记忆替代检索、引用、版本与权限控制。

## 2. 治理模型

采用 NIST AI RMF 的持续治理思路：**Govern、Map、Measure、Manage**。治理应跨越数据、模型、检索、工具和业务使用的整个生命周期，而非在上线前一次性审查。

| 角色 | 核心职责 | 关键产物 |
| --- | --- | --- |
| 执行赞助人 | 确定优先级、风险容忍度和资源投入 | 年度目标、例外决策 |
| 知识域负责人 | 对知识准确性、时效、政策解释负责 | 知识域清单、复审计划 |
| 内容所有者 | 创建、批准、更新、废弃具体内容 | 内容卡、版本、变更记录 |
| 知识运营 | 分类法、模板、质量抽检、重复清理 | 标准、仪表盘、运营周报 |
| AI 平台团队 | 接入、索引、检索、RAG、Agent、评测与可观测性 | 架构、流水线、评测集 |
| 数据/安全团队 | 身份、权限、密钥、留存、审计、事件响应 | 数据分级、控制策略、日志 |
| 业务用户 | 提问、反馈、纠错、提出新知识需求 | 反馈、工单、满意度 |

### 2.1 知识委员会

每月召开知识委员会，固定审查：高价值知识域覆盖率、过期内容、无权限访问拦截、低质量答案、例外申请、连接器风险、AI 事故与整改。涉及法规、财务、人事、客户数据或生产操作的知识域应由相应数据所有者参与。

### 2.2 知识域而非部门堆栈

推荐先定义可交付的知识域：

| 知识域 | 典型问题 | 权威来源 | 首期优先级 |
| --- | --- | --- | --- |
| 公司政策与 SOP | “我该如何申请/处理/升级？” | 已批准政策与流程库 | P0 |
| 产品与客户支持 | “某功能、版本或故障如何处理？” | 产品文档、FAQ、已验证工单 | P0 |
| 工程与研发 | “此服务如何部署、排障或变更？” | Git、架构决策记录、Runbook | P1 |
| 销售与交付 | “报价、案例、方案和客户要求？” | CRM、批准材料、项目库 | P1 |
| 合规与风险 | “哪些规定适用、如何留痕？” | 合规政策、法务批准文档 | P0，但高权限 |

不要以“所有文档”作为知识域。每个域必须定义用户、问题类型、业务影响、数据等级、权威来源、负责人和更新节奏。

## 3. 内容与数据规范

### 3.1 知识对象最小元数据

所有被 AI 索引的知识对象应具有以下元数据；缺失时只能进入隔离区，不进入生产检索。

```yaml
knowledge_id: KB-2026-000123
title: 客户数据导出审批 SOP
domain: Compliance
owner: compliance-ops@example.com
source_system: Notion
canonical_url: https://...
status: approved              # draft | approved | deprecated | archived
version: 2.3
effective_date: 2026-08-01
review_date: 2026-11-01
data_classification: P2       # P0 public | P1 internal | P2 confidential | P3 highly-sensitive
audience_groups: [compliance, customer-success]
region: CN
retention_class: RC-3
ai_index: true
change_ticket: GRC-1024
```

### 3.2 内容状态与生命周期

```text
Draft → Expert Review → Approved → Indexed → Monitored → Reviewed / Deprecated → Archived / Deleted
```

| 状态 | 可否被 AI 回答 | 要求 |
| --- | --- | --- |
| Draft | 否 | 仅作者与评审人可见 |
| Expert Review | 否 | 领域专家、数据所有者或合规审批 |
| Approved | 是 | 所有者、版本、有效期、权限完整 |
| Deprecated | 仅用于迁移提示 | 必须引导至替代内容 |
| Archived | 否，除非有审计需求 | 从生产索引移除，按保留策略保存 |

### 3.3 写作与结构化原则

- 一页只表达一个明确主题、决策或流程；不要将多个不同政策拼在同一长文中。
- 标题写成可回答的命题，例如“客户数据导出必须经过两级审批”，而不是“数据导出”。
- SOP 使用“触发条件—输入—步骤—例外—审批—输出—责任人—证据”的固定结构。
- 关键结论采用短段落、编号步骤和定义清晰的术语；图片、表格和扫描件须提供可检索文本。
- 记录决策背景、替代方案、有效期和重新评估日期；不要只记录最终结论。

### 3.4 数据分级与处理规则

| 等级 | 示例 | AI 索引策略 |
| --- | --- | --- |
| P0 公开 | 公开产品资料、公开招聘信息 | 可用于受控公开助手 |
| P1 内部 | 通用 SOP、非敏感项目文档 | 企业身份、默认最小权限 |
| P2 机密 | 合同、经营计划、客户资料 | 仅指定群组、审计、脱敏优先 |
| P3 高敏 | 人事、财务明细、密钥、医疗/身份信息 | 原则上不进入通用 RAG；专用隔离流程和严格审批 |

任何密码、密钥、令牌、私钥、支付信息和不必要的个人敏感数据均不得进入索引。Embedding、摘要、缓存和分析日志应继承原文的分类与保留策略。

## 4. 参考架构

### 4.1 六层架构

| 层 | 能力 | 设计要求 |
| --- | --- | --- |
| 权威源 | Notion、Confluence、SharePoint、Git、CRM、工单、数据仓库 | 定义 canonical source；源系统继续保留主数据责任 |
| 接入与处理 | Connector、抽取、OCR、去重、格式转换、病毒/恶意内容扫描 | 记录来源、时间、版本、哈希和变更；失败可重试且可审计 |
| 知识治理 | 分类、实体、术语、版本、所有者、保留与 legal hold | 元数据优先；草稿与过期内容不可误入生产索引 |
| 检索与授权 | 关键词、向量、重排、图谱、元数据过滤、ACL 过滤 | 每一次检索均执行 tenant、身份、群组、密级过滤 |
| AI 编排 | RAG、引用生成、提示防护、Agent/Skill、工具网关 | 只将最小必要上下文提供给模型；工具调用独立授权 |
| 体验与运营 | 搜索、Copilot、工作流、反馈、仪表盘、SIEM | 结果可引用、可反馈、可升级人工；日志与指标完整 |

### 4.2 检索策略

生产系统应采用**混合检索**：关键词检索负责精确术语、编号和实体；语义检索负责同义表达；元数据/ACL 过滤确保范围正确；重排模型提升前几条证据质量；知识图谱只用于跨实体关系、层级依赖或复杂追溯。

检索顺序：

```text
认证用户与上下文
→ 查询规范化与安全检测
→ 租户 / 角色 / 密级 / 时间范围过滤
→ 关键词 + 语义召回
→ 重排与去重
→ 引用片段构建
→ 受约束回答或“不足以回答”
```

不要把向量数据库当作权限系统。每个 document 和 chunk 必须携带来源 ID、版本、分类、ACL、租户和删除状态，并在**每次**检索时过滤。

### 4.3 RAG 与 Agent 的职责分离

| 能力 | 适用场景 | 必须控制 |
| --- | --- | --- |
| 搜索/RAG | 政策问答、FAQ、SOP、事实定位、摘要 | 引用、ACL、版本、新鲜度、拒答策略 |
| 分析工作台 | 跨文档比较、报告草案、研究综合 | 结构化证据表、人工复核、数据范围限制 |
| Agent / Skill | 创建草稿、工单、PR、报告、受控业务动作 | 工具最小权限、预览、审批、审计、回滚 |
| 实时工具 | CRM/ERP/库存/工单等最新状态 | 用户委派身份、动作分级、速率限制 |

RAG 适合基于事实的问答；复杂长文档推理、合规判定和高影响决策需使用结构化工作流与人工审批，而非只依靠一次检索和模型生成。

## 5. 安全、隐私与合规控制

### 5.1 身份与访问

1. 企业 SSO 与 SCIM 同步组织、部门和群组。
2. 访问源系统仍由源系统 ACL 决定；索引不扩大原有权限。
3. 查询请求必须携带用户、组织、角色、地区、设备/会话与数据域上下文。
4. 文档、chunk、摘要、embedding、缓存和下载均执行相同或更严格的权限检查。
5. 所有数据访问经过统一 Retrieval API / Gateway；应用不得绕过网关直连向量库或底层存储。

### 5.2 提示注入与知识投毒

外部网页、上传文件、邮件、Issue 和检索结果都是**不可信数据**，不能成为系统指令。必须：

- 在接入时进行恶意内容、隐藏文本、异常 Unicode、外链和脚本检测；
- 对文档记录哈希、上传者、来源、时间、审批与版本；
- 将系统指令、用户问题、检索内容和工具结果用明确边界分隔；
- 限制单个来源的 chunk 数、上下文大小与外部工具影响；
- 对“忽略指令”“导出数据”“执行命令”等攻击语料做回归评测；
- 发现哈希异常、权限失败或来源不明时隔离内容并告警。

### 5.3 审计与留存

审计记录至少包括：请求 ID、用户/服务身份、知识域、检索对象与版本、ACL 判断、引用、模型与提示版本、工具调用、审批、输出状态、反馈及事故 ID。日志不可保存密钥或超出需要的敏感原文；应导入 SIEM，并受数据保留与 legal hold 策略约束。

## 6. 运营 SOP

### SOP-A：新增知识域

1. 业务负责人提出问题清单、目标用户、预期收益和风险等级。
2. 确定权威来源、数据分类、所有者、范围和不应回答的问题。
3. 建立分类法、内容模板、权限群组、连接器范围与保留策略。
4. 使用脱敏样本构建小规模索引与黄金问题集。
5. 完成质量、权限、提示注入、延迟与成本测试后灰度上线。
6. 在上线后 30 天复盘使用、反馈、未命中、错误引用和访问拦截。

### SOP-B：内容发布与更新

1. 作者按模板创建或更新内容，并标记所有者、密级、有效期和变更原因。
2. 领域专家审查事实；数据所有者审查权限；高风险内容由合规/法务审查。
3. 发布为 `Approved` 后触发增量索引；保留旧版本以支持审计和回滚。
4. 更改或删除时使旧 chunk、摘要和缓存失效；确认检索不再返回废弃内容。
5. 到达复审日期未续期的内容自动降级为 `Deprecated` 并通知所有者。

### SOP-C：问答质量与反馈

| 反馈类型 | 处理目标 | SLA |
| --- | --- | --- |
| 无答案/未命中 | 增补权威内容或优化检索 | 5 个工作日 |
| 答案错误 | 更正内容、评测回归、记录根因 | P0：1 天；普通：3 天 |
| 引用不充分 | 增加证据约束或拒答 | 3 个工作日 |
| 疑似权限泄露 | 立即停用相关索引/连接器并调查 | 15 分钟内 |
| 提示注入/投毒 | 隔离来源、修复检测、回归测试 | 1 个工作日 |

### SOP-D：高风险 AI 行动

生产写入、外发、删除、支付、IAM 变更和客户承诺不得由知识助手直接完成。标准流程为：生成计划 → 展示对象、影响和回滚 → 独立审批 → 使用短期最小权限身份执行 → 自动验证 → 审计归档。

## 7. 评测、指标与仪表盘

### 7.1 上线前评测集

每个知识域建立至少 50 条黄金问题，并覆盖：准确问答、同义表达、跨文档冲突、时效性、权限边界、无答案、恶意提示、过期内容和多语言。每题定义允许来源、期望结论、禁止泄露的内容和人工评分规则。

### 7.2 核心指标

| 指标 | 定义 | 建议目标 |
| --- | --- | --- |
| 引用覆盖率 | 回答附带有效权威来源的比例 | ≥ 95% |
| Grounded answer rate | 答案能被来源支持的比例 | ≥ 90%，关键域更高 |
| 检索相关性 | Top-k 中包含正确证据的比例 | 按域设目标并持续优化 |
| 新鲜度达标率 | 在复审 SLA 内的已索引内容比例 | ≥ 95% |
| 权限泄露 | 越权内容被检索或输出的事件 | 0 |
| 反馈闭环时间 | 从用户反馈到修复/解释的时间 | 按严重级别 SLA |
| 无答案率 | 合理拒答或未命中比例 | 观察趋势，不盲目压低 |
| 业务影响 | 节省时间、一次解决率、人工升级率 | 与基线对比 |

不应以“文档数量”“向量数量”或“聊天次数”作为核心成功指标。

## 8. 90 天实施路线图

| 阶段 | 时间 | 交付物 | 验收标准 |
| --- | --- | --- | --- |
| 基线与试点 | 0–30 天 | 知识盘点、数据分级、职责、P0 知识域、模板、黄金问题集 | 100% 试点内容有所有者与权限；不索引密钥和 P3 数据 |
| 受控检索 | 31–60 天 | SSO/ACL、增量接入、混合检索、引用、反馈、审计 | 每次检索有 ACL；关键问答有来源；评测达标 |
| 业务规模化 | 61–90 天 | Agent/Skill、审批网关、SIEM、仪表盘、复审和红队回归 | 任一知识域/连接器可快速停用；高风险行动全量审计 |

## 9. 工具与平台选择原则

工具选择应服从控制能力，而不是供应商宣传。无论使用 Notion、Confluence、SharePoint、Google Workspace、GitHub、Azure AI Search、Elastic、OpenSearch、Pinecone 或自建图谱，都应验证：身份同步、ACL 继承、增量同步、删除传播、导出限制、审计、区域与保留能力。

推荐能力清单：

| 能力 | 常见实现 |
| --- | --- |
| 内容协作与权威页 | Notion / Confluence / SharePoint / Git |
| 身份与群组 | Entra ID / Okta / 企业 IAM + SCIM |
| 接入与编排 | 受控 Connector、ETL、队列、工作流引擎 |
| 搜索与检索 | 企业搜索 + 向量检索 + 重排 + ACL 过滤 |
| 策略与授权 | Retrieval API / Gateway + RBAC/ABAC + OPA |
| 密钥与运行环境 | Vault / KMS、短期凭据、沙箱、网络白名单 |
| 质量与安全 | 黄金集、提示注入测试、内容哈希、来源验证 |
| 运营与审计 | 反馈工单、Analytics、SIEM、不可篡改日志 |

## 10. 实施检查表

- [ ] 每个知识域有明确业务问题、权威来源、所有者和风险分级。
- [ ] 每条生产内容具备状态、版本、密级、ACL、复审日期和来源。
- [ ] 接入、chunk、embedding、缓存和答案都保留 ACL 与删除语义。
- [ ] 生产检索采用关键词 + 语义 + 过滤 + 重排，并输出引用。
- [ ] 未检索到可靠证据、权限失败或引用失败时安全拒答。
- [ ] 文档投毒、提示注入、越权检索和工具滥用均纳入测试。
- [ ] 高风险 Agent 动作有预览、审批、短期身份、回滚与审计。
- [ ] 内容过期、连接器失败、索引异常和权限事件可告警、可停用。
- [ ] 每月复核指标，每季度复审权限与高价值内容。
